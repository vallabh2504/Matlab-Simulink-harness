# MATLAB Engineering Harness engineering workflow

For native Simulink work, add the canonical matlab helper folder and run the complete owned operation inside engineering.withRuntime. Cache/codegen must stay in owned temporary folders; saved models belong in explicit project/output directories. Preserve caller path/configuration and unrelated unsaved models on success and failure.

Use the same canonical skills and standards in Codex, Claude Code or another supported runtime. Actual spawning belongs to the runtime: inspect available tools, never invent a MATLAB MCP subagent API. One accountable orchestrator owns requirements, scope, resources, checks and handoff. Parallelize only separately owned artifacts; serialize MATLAB sessions, `.slx`/dictionary writes and shared state.

1. Discover intent and actual project/environment. Run `matlab-harness preflight`; inspect current files and `matlab-harness resume`. Select only relevant skills with `matlab-harness skills --task ...`. Do not force Simulink or plotting into a MATLAB-only task.
2. Write/version requirements.md with stable IDs, units/ranges/provenance, assumptions, interfaces, governing equations, acceptance methods and exclusions. Obtain actual user approval for substantial new consequential work. Record approval source with `matlab-harness approve`; the command does not grant authorization on its own.
3. Have an independent reviewer challenge requirements and mathematical/system architecture. Freeze task-specific executable acceptance commands and independently owned evaluator assets before builders. `matlab-harness configure-checks --plan ...` binds command names to exact argv lists.
4. Claim one project orchestrator and lease bounded artifact paths to native workers. Handoffs include requirement IDs, interfaces/units, sources, assumptions, exact ownership, budget, expected outputs and evidence. Unsupported parallel runtimes execute sequential roles honestly; self-role review cannot satisfy an independent gate.
5. Implement readable source and valid models; run actual simulations and independent numerical/regression checks through `matlab-harness run-check`. Inspect saved models and executed parameters, not script intention or stale caches. Classify unsupported tests honestly and keep negative evidence.
6. Review meaningful implementation and integrated execution; import actionable findings bound to `matlab-harness snapshot`. A hard check failure, stale evidence or unresolved CRITICAL/MAJOR cannot be offset by a score. Repair in bounded owned changes, retest and obtain independent closure. Reassess counterevidence; escalate unresolved material disputes without altering approved requirements.
7. At handoff, finish active leases, preserve editable source/model/configuration, raw results/figures, traceability, open defects, limitations and reproduction commands. Run `matlab-harness gate handoff` and accept lifecycle checkpoints in order. Do not claim a verified release from file presence, mocked output, high scores or skipped required tests.

During a user question or approval wait, keep the checkpoint incomplete; do not silently approve or force continuation. Durable records are project-local. `revise` archives the old baseline; explicit owner/lock recovery preserves interrupted work. All write-capable participants can bypass local records; independent review, grader quality and process isolation remain necessary.

Models by role are configurable in each native runtime. Use model IDs and tools that are actually available; parallel spawning and continuous execution depend on the runtime. Record the runtime, model, tools, OS and MATLAB release with the evidence.
